# 农链追溯：数据结构与判定说明

> 配套 `main.py` 中的 `traceBatch` / `auditColdChain` / `checkResidues` 三个工具。
> 数据文件：`.agents/agri-data/batches.json`（批次档案）、`.agents/agri-data/gb2763-limits.json`（农残规则表）。
> 全部为教学演示数据，非真实业务数据。修改前备份：`main.py.bak-20261109`。

---

## 1. 已具备的能力

| 项 | 说明 |
| --- | --- |
| 批次追溯 | 按批次号 / 产品名 / 产地查全链路：产地基地、采收预冷、分级打包、质检明细、冷链、承运路线、下游流向 |
| 温度判定 | 逐条比对区间，聚合成超限时段，给出峰值与偏离幅度 |
| 分段控温 | `cold_chain.segments` 按时间落段，支持冷冻干线 -20~-15℃ + 销地冷藏 0~4℃ 这类多段链路 |
| 记录缺口 | 相邻记录间隔 > 6 小时判缺口 |
| 首末衔接 | 采收/发运时间比对首条记录、到货时间比对末条记录，超 6 小时报「开头/收尾无温控」 |
| 累计暴露 | 按相邻记录线性插值，算出「高于上限累计多少小时、低于下限累计多少小时」 |
| MKT | 平均动力学温度（ΔH/R=10000K），分段批次按段分别计算 |
| 时间解析 | 容忍带秒、`T` 分隔、斜杠日期、ISO 时区；解析失败会明确报出，不再静默丢弃 |
| 农残核对 | `checkResidues` 用规则表逐项比对，区分达标 / 超标 / 不属 GB 2763 / 限值未核验 |
| 数据完整性 | 单列「时间无法识别 / 温度缺失 / 无法归属区间 / 顺序倒置」各多少条 |

## 2. 批次档案字段

```jsonc
{
  "batches": [
    {
      "batch_id": "SC20261012-01",       // 批次号，主要检索键
      "product": "赣南脐橙",              // 产品名，参与关键词匹配
      "category": "鲜食柑橘",
      "grade": "一级",
      "owner": "合作社/企业名",
      "trace_code": "SC2026101201000001",
      "origin":   { "province": "", "county": "", "base": "", "supplier": "" },
      "harvest":  {
        "date": "2026-10-12",             // 只有日期时不做小时级衔接判定（避免误报）
        "start_time": "2026-10-12 06:00", // 有才参与「开头是否有温控」判定
        "method": "", "precool": ""
      },
      "packing":  { "plant": "", "date": "", "package": "", "qty": "" },
      "quality":  {
        "inspection_date": "", "lab": "", "conclusion": "",
        "items": [ { "name": "", "value": "", "unit": "", "limit": "", "ok": true } ]
      },
      "cold_chain": {
        "mode": "冷藏运输（5~12℃）",
        "target_low": 5, "target_high": 12,   // 整批区间；有 segments 时作兜底
        "device": "",
        "segments": [ { "label": "", "from": "", "to": "", "target_low": 0, "target_high": 0 } ],
        "records": [ { "time": "2026-10-12 08:00", "temp": 8.2, "place": "" } ]
      },
      "logistics": { "carrier": "", "ship_date": "", "arrive": "", "route": [] },
      "downstream": [ { "buyer": "", "qty": "", "ship": "" } ],
      "notes": ""
    }
  ]
}
```

**分段边界**：`from` 含、`to` 不含。以 `2026-10-17 08:00` 为界时，`08:00` 整点记录归入第二段。

## 3. 冷链判定规则

### 3.1 温度判定
1. 按记录时间找所属区间：有 `segments` 按时间落段，否则用 `target_low/target_high`
2. 高于上限或低于下限记为超限
3. 连续超限记录（相邻 ≤ 6 小时且同段）合并为「超限时段」
4. 峰值取偏离幅度最大的一条，注明高于上限还是低于下限

### 3.2 记录缺口
相邻两条有效记录间隔 > 6 小时（`COLD_RECORD_MAX_GAP_HOURS`）记为缺口。

### 3.3 首末衔接
- 开头：`harvest.start_time`（缺则 `harvest.date` → `ship_date` → `packing.date`）对首条记录
- 收尾：`logistics.arrive` 对末条记录
- 记录早于起点、晚于到货超 1 小时 → 报「时间疑似录错」
- **只有日期精度（无时分）的字段不参与小时级判定**，否则 `00:00` 会把正常批次误报成缺 8 小时

### 3.4 累计暴露（新增）
不是数「几条超温」，而是算「超了多久」：
- 相邻两条记录**限值相同**时按温度线性插值找穿越时刻，只计穿越后的那段。例：10:00 是 7.2℃、14:00 是 11.8℃、上限 8℃，则超限时长 = 4h × (1 − 0.8/4.6) ≈ 3.3 小时
- **跨段**（两条记录分属不同 `segments`）或限值缺失时不做插值，按两端各半计入，报告注明「按两端各半估算」
- 间隔超过 6 小时的区间没有记录，**不计入**暴露时长，另在报告里写「缺记录 X 小时未计入，实际暴露可能更长」
- 低于下限的反向超限同样计算

### 3.5 MKT（新增）
平均动力学温度，ICH Q1A 公式：

```
MKT = (ΔH/R) / −ln( Σ exp(−ΔH/R · 1/Ti) / n )      ΔH/R = 10000 K，Ti 为开尔文温度
```

- 用于衡量「温度波动的等效恒温」，MKT 高于规定上限说明整体热暴露偏重
- **只作参考指标，不作合格判定依据**（新鲜果蔬没有统一的 MKT 判据）
- **分段控温批次按段分别计算**，不输出全局值——冷冻段 −18℃ 与冷藏段 3℃ 混算没有物理意义

### 3.6 结论优先级（从重到轻）

| 条件 | 结论 |
| --- | --- |
| 存在超限时段 | **不合格**：复核装卸与暂存、评估品质，视情冻结流向并追溯用药记录 |
| 无超温但有记录缺口 / 首末衔接缺失 | **待补充**：无法证明全程受控，补齐记录后方可放行 |
| 数据完整性有问题（时间读不懂、温度缺失、段落归属不到） | **待补充**：需人工核实原始记录 |
| 以上都没有 | **合格**：全程受控，可正常放行 |

报告末尾固定附「限值取自示例值、非权威标准」，避免拿演示数据当执法依据。

## 4. 农残核对（checkResidues）

规则表 `.agents/agri-data/gb2763-limits.json`：

```jsonc
{
  "standard": "GB 2763《食品安全国家标准 食品中农药最大残留限量》",
  "rules": [
    { "pesticide": "毒死蜱", "aliases": ["chlorpyrifos"],
      "commodity": "柑橘类水果", "commodity_keys": ["柑橘", "橙", "橘", "柑", "柚", "柠檬"],
      "mrl": 0.05, "unit": "mg/kg", "verified": false, "source": "", "note": "" }
  ],
  "out_of_scope": [
    { "name_keys": ["铅", "镉", "砷"], "reason": "污染物限量查 GB 2762，不在 GB 2763 范围" },
    { "name_keys": ["菌落总数", "大肠菌群"], "reason": "微生物指标查 GB 29921" },
    { "name_keys": ["糖度", "可滴定酸", "硬度", "果径", "横径"], "reason": "属于品质指标，非食品安全限量" }
  ]
}
```

判定分四种结果：

| 结果 | 条件 |
| --- | --- |
| 超标 | 实测值 > 规则表 MRL |
| 达标 | 实测 ≤ MRL 且该条 `verified: true` 且档案未标记超标 |
| 未超标但限值未核验 | 实测 ≤ MRL 但 `verified: false` |
| 不属本范围 | 命中 `out_of_scope`（重金属 / 微生物 / 品质指标） |
| 无法核对 | 规则表无对应药名或对应作物 |

**`verified` 是这套机制的关键**：只有核对过标准原文的条目才能标 `true`，标 `true` 后才会给「达标」结论，否则一律降为「需核对」。当前表内 6 条全部 `verified: false`，所以默认输出的是核对清单而不是合格判定——这是有意为之，避免用未核验的数值冒充国标。

数值解析支持：`0.02`、`未检出`（按 0）、`＜10`（记为上界）、`8.0×10³` → `8000`、`1.2e3`。

用 `py -3.13` 导入 `main.py` 直接调用工具（不启动 TUI）：

| --- | --- | --- | --- |

| GX20261020-05 沃柑 | 装卸区超温 + 12h 缺口 | 不合格（峰值 12.4℃） | 14.9 小时 / MKT 8.8℃（高于上限） |
| SC20261018-03 红阳猕猴桃 | 温度正常，10h 缺口 | 待补充 | 0 小时（缺记录 10h 未计入）/ MKT 2.5℃ |
| LN20261015-02 冷冻草莓 | 分段控温 | 合格（20/20 条） | 0 小时 / 段1 MKT −18.2℃、段2 MKT 2.7℃ |

| 批次 | 结论 |
| --- | --- |
| SC20261012-01 | 需核对（1 项限值未核验） |
| GX20261020-05 | **不合格**（克百威 0.08 > 表内 0.02） |

工具注册：`TOOLS` 与 `TOOL_HANDLERS` 均为 10 项且完全对应（新增 `checkResidues`）。

## 6. 仍然做不到的事（有意留简单）

1. **不做多方写入与防篡改**：档案是一个静态 JSON，谁写谁改没有来源签名与时间戳。要作为对外凭证，需产地/实验室/承运/销地各自写入并加哈希链或签名，本项目没有做。
2. **规则表未与标准原文核验**：6 条 MRL 均为示例值，`verified: false`。要用作放行依据，必须逐条核对 GB 2763 原文并填 `source`。
3. **MKT 没有合格判据**：只输出数值与「是否高于规定上限」，新鲜果蔬无统一 MKT 标准。
4. **一次最多展开 3 个批次**（`TRACE_MAX_BATCHES`），大批量核查要拆多轮。
5. **匹配是子串包含**：关键词「信丰」会命中所有信丰产地批次，不分词、不排序。
6. **跨段累计暴露是近似值**：分段边界那一个区间按两端各半估算，报告会注明。

## 7. 维护方法

**新增批次**：复制 `batches.json` 里任一对象改字段。`batch_id`/`trace_code` 唯一；`product`/`origin.county`/`owner` 会被关键词命中；温控记录按时间升序写。

**新增农残规则**：在 `gb2763-limits.json` 的 `rules` 里加一条，`commodity_keys` 写该限值适用的作物关键词。核对完标准原文后把 `verified` 改为 `true`，并在 `source` 填标准条目号。

**调整判定口径**：`COLD_RECORD_MAX_GAP_HOURS`（缺口阈值，默认 6 小时）、`TRACE_MAX_BATCHES`（单次展开批次上限）、`AUDIT_MAX_OUTPUT`（审计报告字数上限）、`MKT_DH_OVER_R`（MKT 的 ΔH/R，默认 10000K）。
