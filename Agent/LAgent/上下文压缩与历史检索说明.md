# LAgent 上下文压缩与历史检索（实现说明）

> 目标：让 Agent 在有限的上下文窗口里持续完成长任务。
> 方案：**不用向量库、不用 Embedding、不引第三方检索框架**，只用「本地 jsonl 归档 + 关键词全文检索 + 一次 LLM 摘要」。
> 全部改动集中在 `main.py`（单文件，便于阅读和维护），另加两个配置项。

---

## 1. 整体流程

```
用户输入 / LLM 每轮回复
        │
        ├─▶ stream_once() 拿到回答 + usage（拿不到就本地估算）
        │
        ├─▶ _sync_status()  刷新状态条；≥70% 首次告警 + 暂停接收普通提示词
        │
        └─▶ 用户输入 /compact
                  │
                  ├─① save_context_archive()  写 .agents/context/<编号>.jsonl
                  │    写盘 + 回读校验（每行合法 JSON、条数一致）不通过就中止
                  │
                  ├─② request_summary()  用 COMPACT_PROMPT 让 LLM 生成约 5,000 Tokens 摘要
                  │    请求里**不带 tools** → 压缩期间不可能发生工具调用
                  │
                  └─③ 用摘要替换 messages
                       messages = [system（原样保留）, user(摘要 + 归档说明)]
                       清空 usage 基线 → 解除输入限制
```

失败时（归档失败 / 摘要请求失败 / 摘要为空）**不改动原 messages**，状态条仍按原规则判定，可再次执行 `/compact`。

## 3. 阈值与状态规则

| 情况 | 行为 |
| --- | --- |
| 占用 < 50% | 状态条绿色 |
| 50% ~ 70% | 状态条黄色 |
| ≥ 70% | 状态条红色 + 日志告警 + **暂停接收普通提示词**（只认 `/compact`） |
| 压缩进行中 | 状态条显示「压缩中」；普通提示词直接拒绝；不执行任何工具 |
| 压缩成功 | 解除限制；如果压缩后基线仍 ≥ 60%（窗口相对摘要太小，压不动了），改用 **95%** 硬上限，并在日志里说明 |
| 压缩失败 | 原上下文不变，提示错误，可重新 `/compact` |

`usage` 来源优先级：**模型 API 返回的 `usage`（prompt+completion）** → 之后新增消息按估算叠加 → API 没给就直接整体估算。

## 4. 状态条（TUI 顶部）

```
上下文 12.4k / 128k（默认） · 已占用 9.7%
```

- `12.4k` 当前会话已用 token（含 System Prompt、工具定义、对话历史、工具调用与返回）
- `128k` 模型上下文窗口；来源依次为 `配置` / `API` / `默认`
- 显示「（默认）」就表示没探测到真实窗口，按 128k 处理
- 压缩中 / 被暂停 / 窗口偏小这几种状态会在同一行前缀额外提示

## 5. 归档格式

目录：`项目根\.agents\context\`（可用 `[context] dir` 改到别处）
文件名：`20261022-153000.jsonl`（`YYYYMMDD-HHMMSS`，同秒重复自动加 `-2`）

一行一条原始消息，字段完全沿用 OpenAI 消息格式，所以顺序、角色、工具调用参数、工具返回结果都在：

```json
{"role":"user","content":"帮我看看 main.py"}
{"role":"assistant","content":null,"tool_calls":[{"id":"call_1","type":"function","function":{"name":"RunCli","arguments":"{\"command\":\"powershell\",\"args\":[\"-c\",\"dir\"]}"}}]}
{"role":"tool","tool_call_id":"call_1","content":"...命令输出..."}
```

检索时「第 N 条」就是这里的行号，方便定位。

## 6. `recallContext` 工具

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `text` | 是 | 关键词，多个用空格分隔（需**全部**命中） |
| `id` | 否 | 只在该归档编号内检索；不传则检索全部归档 |

返回：匹配数量 + 每段的「归档编号 / 第几条 / 角色 / 原文片段（命中位置前后各约 130 字）」。
限流：单次最多 8 段、单归档最多 3 段、总长度 ≤ 3000 字符（避免检索结果又把上下文占满）。
异常输入：编号带 `..`/路径分隔符直接拒绝；编号不存在时列出可用编号。

```ini
[llm]
context_window =          ; 留空=先问 /models，拿不到按 128k 并显示「默认」；可写 128k / 65536 / 131072

[context]

```

> 注意：`config.ini` 必须存成 **UTF-8 无 BOM**，否则 `configparser` 会报 `MissingSectionHeaderError`。

## 8. 设计取舍

1. **为什么不抽成独立模块**：原项目就是单文件（`main.py`），拆文件会让「压缩 → 归档 → 检索」三件事分散；这里用分节注释把它们放在一起，逻辑顺序和阅读顺序一致。
2. **为什么不把摘要放进 `system`**：`system` 要原样保留（技能列表、工具约定都在里面）；摘要作为**第一条 `user` 消息**最省事，也符合「续接会话」的常见做法。
3. **归档先落盘再压缩**：压缩不可逆，先把原始上下文写实、并回读校验，才允许继续。
4. **压缩请求不带 tools**：从协议层面堵死「压缩期间调用工具」，不靠程序判断。
5. **70% 告警 / 95% 兜底**：70% 留出足够空间让摘要请求本身能发出去（摘要输入 + Prompt 仍远小于窗口）；只有当窗口小到「压缩后仍压不下去」时才放宽到 95%，否则会出现「压一次锁一次」的死循环。
6. **估算公式偏保守**：中文按 1 字 1 token，会比真实分词略高，宁可早告警，不要爆窗。

## 9. 已验证行为

用本地假 OpenAI 兼容服务（`/v1/models`、流式 `/v1/chat/completions`、非流式摘要接口）跑了 51 项自测，全部通过，覆盖：

- 窗口探测：从 `/models` 取到 65536（来源 API）；配置 `128k` 解析正确；真实环境无 key 时回退 `128000 + 默认`
- 压缩：归档条数/角色顺序/工具调用参数/工具返回全部保真；编号格式正确；系统提示对象未被替换
- 摘要请求：system 用的是 `COMPACT_PROMPT`，且**不含 `tools`**
- 检索：全局检索、按 id 检索、无匹配、非法编号、不存在编号、缺 `text` 报错、长度上限
- 失败路径：摘要接口报错时 messages 不变、归档仍在
- TUI：状态条内容（`k / k · %`、「默认」标注）、正常对话、越过 70% 暂停、`/compact` 解锁、压缩中新输入被拒、小窗口兜底提示
- 兼容性：服务端若拒绝 `stream_options`，自动退回不带 usage 的请求，对话不受影响（此时 token 数退化为估算）

## 10. 已知限制（有意留简单）

1. 检索是**子串匹配**，不做分词 / 同义词 / 排序打分（多关键词按「命中个数」简单排序）。
2. 归档不会自动清理，长期使用建议定期删掉旧的 `.agents\context\*.jsonl`。
3. `usage` 依赖服务端支持 `stream_options.include_usage`；不支持时退化为估算，可能与真实值有偏差。
4. 压缩是**一次性请求**：如果历史本身超过单次请求上限，会丢弃较早消息（日志和摘要里都会注明「已完整归档，可用 recallContext 检索」）。
5. 摘要质量依模型而定；Prompt 里已明确要求区分「已验证事实」与「未验证推测」。
